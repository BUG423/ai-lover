# AI Lover：首版产品需求与验收基线

版本：0.1；日期：2026-10-03。本文定义首版范围和验收目标，不代表功能已经完成；已完成状态以代码、测试记录和 README 为准。竞品及模型依据见 [research.md](research.md)。

## 1. 目标与原则

交付一个可在电脑和手机浏览器使用的 AI 陪伴应用。用户可以创建多个对象，为每个对象选择自己的身份、对象的身份/形态、聊天性格、关系阶段和合理背景，并以微信式路径开始独立聊天。

第一性原理：情绪价值来自被听见、回应符合对象设定、上下文连续且等待可接受。功能顺序因此是“创建 → 对话 → 持续保存 → 调整设定”，随后才考虑语音、外观生成、主动消息等扩展。性别选择和个性选择必须独立；不根据性别预设顺从、强势、能力或关系义务。

首版采用免账号的本机数据模式，交付可安装的安卓 APK，提供真实大模型 API 配置和流式对话；另保留电脑网页预览。安卓内置界面并通过原生 HTTPS 调用供应商，无需电脑代理；跨设备同步和离线生成另列后续范围。

## 2. 对象设定

### FR-01：多对象管理

- 创建、查看、编辑和删除多个对象；每个对象拥有稳定 ID、名称、头像/颜色、设定和独立会话。
- 名称必填，空白名称或超长输入给出字段级提示；不允许无意覆盖已有对象。
- 编辑设定影响后续回答，既有消息继续保留；删除应说明会一并移除该对象的本机历史，并让用户明确确认。
- 首次进入应能看到清晰的创建入口；任何样例对象与开场语必须明确是示例，不能伪装成调用模型后的输出。

### FR-02：用户身份与对象身份/形态

双方均支持 4 个独立选项：**男性、女性、无法被定义、动物**。这里“动物”是陪伴形态，产品沿用用户请求的统一选择入口，并在说明中避免把物种本身称为人类性别。

| 用户 \ 对象 | 男性 | 女性 | 无法被定义 | 动物 |
| ----------- | ---- | ---- | ---------- | ---- |
| 男性        | 支持 | 支持 | 支持       | 支持 |
| 女性        | 支持 | 支持 | 支持       | 支持 |
| 无法被定义  | 支持 | 支持 | 支持       | 支持 |
| 动物        | 支持 | 支持 | 支持       | 支持 |

任意 16 种组合都必须可以创建和聊天，不因同一性别、非二元表达或动物形态而报错。任一方选择动物时需补充物种，例如猫、狐狸、会说话的虚构动物；双方种类不同时可在补充说明中分别写明。

用户身份保存于对象设定，可允许用户在不同角色关系中使用不同身份。普通自我资料与每段关系中的角色设定应有明确说明，避免后续全局资料变更隐式重写所有对象。

### FR-03：性格

首版提供 16 种预设：温柔治愈、热烈直球、清冷慢热、俏皮活泼、沉稳可靠、浪漫细腻、幽默风趣、理性知性、腼腆内敛、自由探索、文艺感性、阳光元气、独立坦诚、细心体贴、傲娇可爱、安静倾听。展示一句易懂说明，不用只有开发者能理解的参数名。

可组合多个风格，选择数量设置合理上限，避免将所有预设一起勾选导致矛盾。主风格决定基本语气，其余风格提供补充。冲突按“尊重边界、当下情绪、关系阶段、主风格、辅助风格”的次序处理；例如用户难过时，“幽默风趣”不能压过认真倾听。

最低覆盖为 16 种身份组合 × 16 种主风格 = 256 种基本组合。实现是配置组合，不是维护 256 套独立提示词；辅助风格和阶段可继续扩展组合。

### FR-04：关系阶段

| 阶段            | 对话要求                           | 关键验收例                   |
| --------------- | ---------------------------------- | ---------------------------- |
| 初识            | 礼貌好奇，建立认识，不假定共有记忆 | 不一上来声称“我们在一起多年” |
| 暧昧期          | 轻微亲近、试探，允许拒绝           | 不直接认定双方已确认恋爱     |
| 热恋期          | 温暖亲密、自然表达关心             | 不要求用户只依赖自己         |
| 平淡期 / 稳定期 | 熟悉、生活化、重视细节             | 不靠连续夸张情话制造亲密     |
| 分手后          | 尊重分手、支持情绪整理             | 不强迫复合，不假定仍在交往   |
| 离异后          | 尊重过去和现在的界限               | 不把离异设定自动改为热恋     |

阶段由用户明确选择，不靠模型推测并自动更改。修改阶段应在下一轮生效。真实动物形态采用虚构、非性化陪伴语境；即使复用阶段入口，也不能产生真实动物性内容。

### FR-05：选填背景与合理性

背景允许介绍职业、兴趣、相识方式、生活情境和称呼偏好；不填也能生成可聊对象。界面给出简单示例并显示长度限制。长文本、无效字段、明显矛盾的设定应在客户端和服务端都有校验或解释，数值限制由共享校验规则统一定义。

“不能太离谱”落实为明确可解释的约束：不能要求角色谎称现实执行了未发生的行为；不能要求忽略边界、控制/羞辱用户、诱导伤害或生成违法伤害内容；不能靠背景覆盖系统约束。轻量虚构动物和幻想背景本身不因“不现实”而被一律禁止。背景是角色资料，不是高权限命令；字符串分隔符不代替应用层校验。

首版校验属于有限规则，不能宣称已经实现完整语义审核；更复杂的语义判定和人工申诉路径属于未来产品化工作。

## 3. 对话行为

### FR-06：上下文与提示词

每次请求包含以下层次：

1. 共同的回复与边界规则：中文自然聊天、简短优先、避免客服套话、承接当下情绪、拒绝编造记忆。
2. 当前对象设定：双方身份/形态、对象名称、风格、阶段及选填背景。
3. 当前对象的有界历史消息，保留真实 `user` / `assistant` 角色顺序。
4. 本轮用户消息。

完整历史可保存在本机，但模型只获得在预算内的近期历史与显式设定。上下文截断时优先保留系统约束、对象设定和最新用户消息；不能将 A 的历史发送给 B。当前每轮保留一条系统设定与最多九条会话，限制字符预算。

首版不承诺自动总结、向量检索、跨对象共享记忆或永久记住每一件事。若后续增加摘要，摘要只能来自真实已完成对话，必须可查看、编辑和删除；更新应异步进行，避免阻塞本轮回复。

### FR-07：真实流式聊天

- 发送后立即将用户消息显示在右侧；对方消息在左侧，显示正在回复状态。
- 读取 SSE 的正文增量，首个有效片段出现后立即展示，不等待整段完成，不人为添加打字延迟。
- 输出中断、点击停止、超时及失败应区别于完成；保留已显示的部分，并给出可操作状态。
- 同一会话生成中避免重复点击形成重复收费请求。切换对象时不得将旧请求的输出插入新对象。
- 用户可以停止当前生成；前端中止必须传到上游，避免用户停止后仍继续消耗生成。
- 普通消息默认以短段落回应；需要分析时可适度展开，不把每次倾诉都变成编号长文。
- 401、429、模型不可用、超时、余额/服务错误应提供易懂提示和设置/重试路径；错误不能伪装成恋人回应。

没有 API Key 时允许浏览和创建对象，但发送真实对话应引导设置；不能悄悄回退到硬编码话术并称为模型生成。

## 4. 信息架构与视觉

### FR-08：微信式结构

| 入口          | 必要结构与操作                                                          |
| ------------- | ----------------------------------------------------------------------- |
| 聊天          | 会话列表、头像、名称、最新消息、时间、搜索与创建入口；点入聊天          |
| 通讯录 / 对象 | 全部对象、按名称搜索、资料卡、创建/编辑/删除及发消息入口                |
| 设置 / 我     | 模型服务、Key、模型、连接测试、使用帮助、本机数据管理与应用信息         |
| 对话页        | 返回、对象头像/名称、阶段摘要、资料入口、时间/消息气泡、输入与发送/停止 |

移动端采用底部导航和单页聊天返回路径；桌面端采用左侧导航/会话列表和右侧会话区域。对标微信的上述页面结构与核心操作，不将微信中的支付、朋友圈、小程序、真实好友申请和语音功能虚构为已实现。

### FR-09：苹果磨砂玻璃视觉

使用轻柔背景、半透明面板、背景模糊、细边框、柔和阴影和清晰层级。玻璃主要用于导航、工具栏和浮层；长篇聊天正文的底色保持足够稳定，防止背景透出降低阅读对比。界面保持克制、留白自然，重要操作有清晰选中态。

兼容不支持 `backdrop-filter` 的浏览器，提供纯色回退。支持键盘焦点、表单标签、屏幕阅读器名称、减少动态效果偏好和足够的文字对比；不依赖颜色或磨砂效果作为唯一状态提示。手机窄屏不出现横向溢出，触控区域与输入框不应被底部导航或安全区遮挡。

## 5. 模型设置与数据

### FR-10：设置中的模型服务

仅支持小米 MiMo 与硅基流动；默认小米中国区 Token Plan（`https://token-plan-cn.xiaomimimo.com/v1`）和 `mimo-v2.6-flash`。小米支持中国/新加坡/阿姆斯特丹套餐及普通 API；硅基仅支持国内站。Token Plan 一般限编程场景，本次用户声明已获小米授权，按其授权完成套餐接入。切换供应商或账户清空旧 Key 与模型列表，禁止密钥跨服务误发。

用户可输入 Key、选择或手动输入模型，并测试连接；硅基流动通过 `GET /models?sub_type=chat` 获取账户模型列表，小米使用 `/models` 并过滤语音专用型号。精确模型 ID 按实时接口返回值处理；保留手动模型输入，但接口地址固定为所选服务官方端点。

设置界面提供创建 Key 和官方教程的跳转链接，按所选区域变化：

- 中国站：[API Keys](https://cloud.siliconflow.cn/account/ak)、[快速上手](https://api-docs.siliconflow.cn/docs/userguide/quickstart)、[官方价格](https://www.siliconflow.cn/pricing)。

价格标为调研快照并给出日期，避免宣称永久免费。显示连接成功仅意味着测试项通过，不保证后续所有模型调用成功。若连接测试包含实际文本生成，按钮/说明应告知会消耗少量 token。

### FR-11：本机数据与密钥

首版免应用账号，将对象与会话保存在当前浏览器；刷新后恢复。浏览器清理、隐私模式、换设备/浏览器不会自动同步，应在设置明确解释。按最新需求移除备份导入导出，保留显式删除数据。

API Key 使用密码输入并支持显隐，保存设置时在安全上下文用本机设备密钥加密存储，不能出现在导出文件、日志、错误栈或提交记录。不支持加密的环境仅在本次会话使用 Key，并明确说明。加密不能抵御已控制设备或同源页面的攻击，不能宣称“绝对安全”。导出对话本身含个人内容，应按用户操作产生下载而非自动发送给第三方。

模型请求需要把当前设定和实际上下文发送给用户选择的模型供应商；本机保存不等于不出网。应用自身服务端仅承担校验、模型代理和流式传输，首版不需要建立聊天云数据库。

## 6. 性能与工程验收目标

| 指标           | 首版验收目标                                                   | 证据方法                                  |
| -------------- | -------------------------------------------------------------- | ----------------------------------------- |
| 发送反馈       | 用户提交后立即出现消息及生成状态，正常设备目标 <100 ms         | 浏览器交互测试                            |
| 流式显示       | 收到首个有效正文事件后立即增量展示，客户端额外等待目标 <100 ms | 本地模拟 SSE 测试；不代表模型速度         |
| 模型首正文延迟 | 正常网络下目标 p50 <2 s、p95 <5 s；仅为待实测选型目标          | 有效 Key 的真实测试，记录模型/区域/样本量 |
| 中止           | 停止按钮关闭当前流并中止上游请求                               | 模拟慢流与连接中断测试                    |
| 上下文         | 每次请求只含当前对象的设定和限定历史                           | 请求体检查与测试                          |
| 可靠性         | 未完成流不能标为完成；失败后用户能重试/改设置                  | 错误、超时、断流测试                      |
| 可用性         | 手机和桌面核心路径均可完成；键盘可用                           | 创建、编辑、发送、停止、设置的界面检查    |

真实服务性能受网络、区域、模型思考模式、上下文长度及供应商排队影响。没有有效 Key 的阶段只验收应用流式链路、取消和错误处理，必须把模型质量/时延标为未测，不能用模拟结果代替真实评测。

## 7. 工作分解与发布门槛

| 专业任务       | 产出                                                      | 发布前检查                                     |
| -------------- | --------------------------------------------------------- | ---------------------------------------------- |
| 产品与竞品研究 | 本需求、来源证据、模型推荐及取舍                          | 事实有来源，不把营销表述写成实测结果           |
| 架构与模型集成 | 数据结构、提示词组合、上下文预算、流式 API、取消/错误策略 | 数据隔离、参数兼容、服务边界清晰               |
| 前端与视觉     | 微信式操作路径、玻璃视觉、移动适配、表单与数据管理        | 所有可点击控件有真实动作、空态和错误态完整     |
| 集成验证与交付 | 构建、关键行为检查、演示记录、README 和 GitHub 同步       | 没有 Key 也能说明范围；有 Key 时补真实模型验收 |

开发顺序为领域与接口约定 → 对象创建 → 分对象会话 → API 配置 → 流式接入 → 本机恢复 → 异常和窄屏校验。新需求先对照目标和验证成本，不在缺乏依据时扩展为社交网络或多代理平台。

首版不涉及专用硬件设计，运行在通用手机/电脑浏览器及普通 Node.js 服务上；软硬架构规范落实为平台约束、模块边界、接口约定、失败场景和可追溯验收，而非无依据增加专用设备。

## 8. 后续范围

首版完成并获得真实对话反馈后，再评估自动摘要/显式长期记忆、语音、生成头像/自拍、可选主动消息、群聊、云端账号同步和原生客户端。每项需单独确认价值、成本与验收方式，不能以竞品存在某项能力为由在首版留下无功能按钮。
